CasaOS UI v0.4.25 supports a YAML paste/upload in Custom Install → Import. Its validator requires top-level `name` to match a key in `services`. The template has one service with this exact match. It supplies CasaOS `main`, title, architectures and launcher fields, literal string environment values and a long-form loopback port. Environment-file interpolation is avoided. In the official import round trip, the form merges the original YAML back into its output, preserving user/read_only/cap_drop/security_opt/pids_limit/cpus/logging. Memory is also supplied in deploy.resources.limits because the form reads that field. The image digest must be checked after import: the image/tag controls split strings at colons and should not be used to edit a digest reference.

Launcher metadata points at the approved HTTPS private origin rather than the host's loopback port. Its hostname/scheme/port/index are ordinary display metadata; they do not create a TLS route. Before supplying a final import, verify Jesse's exact CasaOS/AppManagement versions, an unused port, the backend address reachable from the container, and an authorized existing/private HTTPS route. A container's localhost is not the host's localhost. No server/account access or network changes have been performed.

The official AppManagement Update method looks up App Store metadata, so the built-in update button is not an automatic channel for this custom import. PullAndApply does make a .bak copy and starts Compose with Wait, but sets success=true even when UpWithCheckRequire returns an error; it does not establish the required health-based rollback guarantee. No periodic custom-image deployment or reliable automatic rollback was found in the reviewed implementation. Do not claim that an import, restart policy, or healthcheck enables updates.

Minimum update path: one owner-authorized host controller plus a recurring host timer, using the owner's existing Docker access. It polls only the designated public frontend channel, validates/pulls a versioned image, writes its exact digest, waits for backend status/image health and restores the retained prior digest on failure. No Docker socket or credentials go into the application container. CasaOS and the updater must share one stack ownership contract; the existing tested docker/update.py expects service `frontend`, its own runtime.env and deployment state, and deliberately refuses to adopt GUI-created containers. It cannot simply be pointed at this imported stack. An adapter/adoption verification against Jesse's actual version and saved Compose path is still required before enabling it. Keep CasaOS's image-edit/update controls out of the automated channel once controller ownership is established.

Jesse's one-time host action is to grant the operator an already-approved management route, or run an operator-prepared installer that initializes the single app's update state and timer. The operator handles this; Jesse should not build code, manage bundles, create a GitHub PAT, or install a privileged updater container. A verified private web route also needs one owner-approved configuration action if none already exists.
